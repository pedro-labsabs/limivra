# Limivra v0.1.0-rc1 — notas do candidato

**Versão dos pacotes Cargo:** `0.1.0`
**Estado:** artefato de avaliação técnica; não é anúncio de release nem autorização de distribuição pública.
**Data:** 2026-10-21

Estas notas descrevem o código e as evidências presentes na cadeia de branches até a Issue #34. O workspace contém um núcleo Rust e uma CLI inicial; ainda não contém o aplicativo desktop completo. O candidato preserva o fluxo base sem root e não instala APK companheiro no telefone.

## Capacidades por milestone

### M0 — Fundação e viabilidade

- Há decisões registradas para usar scrcpy externo, detectar capacidades com evidência e não exigir root (`ADR-0001` a `ADR-0003`); essas três ADRs continuam `PROPOSED`.
- `ADR-0004` está `ACCEPTED` e o código original está licenciado sob MIT.
- **Reconciliação necessária:** não há arquivo `ADR-0005` no branch-base `9df11b4`. Portanto, estas notas não declaram concluída a série `ADR-0001` a `ADR-0005`. `ADR-0006` documenta o tarball standalone.
- O [SPIKE-001](../research/SPIKE-001.md) contém observações físicas no Redmi Note 13 4G. O resultado é específico ao cenário registrado e não valida toda ROM ou host.

### M1 — Sessão Linux via USB

- O núcleo/CLI incluem descoberta ADB, seleção de alvo, ciclo de vida da sessão e adaptador de transporte scrcpy sem root.
- O registro físico de USB descreve vídeo e teardown no host de teste. O issue #20 continua `OPEN` no GitHub; este RC gate não repete nem fecha a prova ponta a ponta.
- A sessão de vídeo pode permanecer ativa quando a injeção de input é bloqueada pela política da ROM. Os limites observados de input no HyperOS estão descritos nos registros físicos, sem generalização para outras versões.

### M2 — Display virtual e fallback

- Há um provedor de display virtual, lançamento de app e fallback explícito para mirror, além da matriz de compatibilidade.
- O SPIKE-001 registrou criação de display virtual e lançamento de Configurações na ROM ensaiada. Isso não implica suporte universal nem modo desktop multijanela.
- A Issue #23 continua `OPEN`; o estado de código e de evidência é distinto do fechamento do issue.

### M3 — Controles, privacidade e Wi-Fi

- O núcleo mapeia `Ctrl+Shift+D` para desconectar, `Ctrl+Shift+S` para alternar display, `Ctrl+Shift+P` para pausar/retomar vídeo e `Ctrl+Shift+R` para recarregar display virtual. A slice fornece contratos de host control, não uma toolbar ou janela desktop completa.
- A política de input exige consentimento e libera controles pressionados ao perder foco ou sessão. O core não retém texto digitado.
- O pareamento ADB Wi-Fi recebe o código por stdin privado, valida o alvo e usa socket Unix em diretório privado `0700`; os testes usam subprocessos controlados e não são prova de pareamento físico real.
- O launcher do core restringe apps permitidos e vincula a sessão ao display virtual. O registro físico da Issue #29 observou Configurações e Calculadora lançadas sequencialmente no display virtual; o retorno ao host permanece uma intenção sem adaptador gráfico.
- O [SPIKE-028](../research/findings/SPIKE-028-freeform-windowing.md) encontrou uma tarefa de Calculadora em floating/freeform individual, enquanto Configurações permaneceu fullscreen. Não foram obtidas duas janelas livres simultâneas.

### M4 — Hardening e distribuição

- A base da Issue #33 tinha 149 testes do workspace, com contratos herméticos e fakes de processos. Este gate adiciona um teste de integridade do RC; a contagem final é registrada no checklist desta Issue.
- Probes genéricos limitam cada stream a 1 MiB e parsers estruturados limitam linhas a 16 KiB. Os fakes de teardown validam identidade de processo com `pidfd`; isso não é apresentado como garantia universal de produção.
- O repositório contém threat model, `SECURITY.md`, CI Linux e smoke sintético que classifica X11/Wayland e retorna `SKIP` headless. Esses smokes não iniciam um compositor nem comprovam uma sessão gráfica real.
- O empacotador gera um tarball standalone Linux x86_64 e scripts de instalação/remoção sem root. `--remap-path-prefix` remove caminhos da worktree do binário e os archives foram comparados entre caminhos de build distintos.
- O inventário `NOTICES.md` faz triagem de expressões SPDX para 65 dependências travadas; a agregação integral de textos de copyright dos autores permanece pendente para a fase pré-release.

## Limites conhecidos

- **ROM ensaiada:** Xiaomi Redmi Note 13 4G, Android 15 / HyperOS 2, build registrado nas evidências. Na tentativa de duas janelas livres, a Calculadora aceitou floating individual e resize; Configurações ficou fullscreen. O resultado é `FAIL` para duas janelas livres simultâneas neste par de apps e cenário, não uma conclusão universal sobre todas as ROMs HyperOS.
- **Host gráfico:** uma futura sessão interativa requer um servidor Wayland ou X11 disponível. O comando de smoke atual só classifica variáveis do ambiente e produz `SKIP` explícito em headless; não verifica conexão com compositor.
- **Interface:** ainda não há aplicativo desktop completo, toolbar gráfica nem adaptador para executar automaticamente `ReturnToSession`.
- **Distribuição:** o lifecycle de instalação foi exercitado com `PREFIX` temporário no host de build, não numa distribuição Linux limpa. O tarball é para x86_64 e depende das bibliotecas do sistema; SHA-256 não é assinatura digital.
- **Dependências abertas:** Issue #20 permanece `OPEN`; Issues #23 e #25–#34 também aparecem abertas no GitHub nesta revisão, e PR #59 segue aberto apesar da aprovação independente de QA informada para a Issue #33. Aprovação de QA não equivale a merge ou fechamento.
- **Prova física:** nenhum teste físico foi inventado nem executado durante a fase offline do M4. As afirmações físicas acima apontam para os registros empíricos de [SPIKE-001](../research/SPIKE-001.md), [SPIKE-028](../research/findings/SPIKE-028-freeform-windowing.md), [USB/Issue #20](../testing/evidence/2026-10-21-usb-session-qa-evidence.md) e [launcher/Issue #29](../testing/issue-29-launcher-app-controls.md). O estado aberto da Issue #20 continua explícito.
